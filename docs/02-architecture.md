# Архітектура

> **Увага:** замовник спростив задачу — див. `04-admin-and-qr.md`. QR несе лише `{BASE_URL}/i/{ID}`, дані — в адмінці. Розділи 2–5 нижче описують ширшу чернетку (мітки з кодами, події, власники) і підлягають спрощенню після уточнення, які поля потрібні. Для хостингу — розділ 7 у `04-admin-and-qr.md`.

## 1. Стек

1. Python 3.12, Flask (веб-застосунок із серверним рендерингом, без JS-фреймворків).
2. SQLite (один файл `instance/gear.db`) — достатньо для сотень/тисяч одиниць, легко резервувати.
3. `segno` — генерація QR (SVG, корекція рівня H).
4. Адаптивна HTML-верстка (телефон у полі — основний клієнт).

Мало залежностей — навмисно: проєкт має бути простим у розгортанні й підтримці.

## 2. Модель даних

```
holders ──< items >── tags
              │
              └──< events
```

1. **holders** — особа, група або склад: `id, name, kind(person|group|storage), contact, active`.
2. **items** — річ: `id, name, category, inventory_number (унікальний), serial_number, description, acquired_on, cost, status, holder_id, archived`.
3. **tags** — мітка: `code (PK, нормалізований), item_id, kind, location_note, status(active|damaged|lost|replaced), created_at, retired_at`.
4. **events** — журнал (append-only): `id, item_id, type, holder_from, holder_to, tag_code, note, actor, created_at`.

Типи подій: `created`, `transfer`, `audit`, `repair`, `note`, `status`, `tag_issued`, `tag_retired`, `written_off`.

Статуси речі: `in_stock` (на складі), `issued` (видано), `repair`, `lost`, `written_off`.
Передача на `storage`-власника → `in_stock`, іншому → `issued`.

## 3. Код мітки

1. Алфавіт Crockford base32 без неоднозначних символів: `0123456789ABCDEFGHJKMNPQRSTVWXYZ`.
2. 7 випадкових символів + 1 контрольний = 8 символів. Показується як `XXXX-XXXX`.
3. Контрольний символ: `sum((i+1)*val_i) mod 31`. Виявляє одиночну помилку та перестановку сусідніх символів.
4. Нормалізація введення: регістр ігнорується, дефіси/пробіли відкидаються, `O→0`, `I/L→1`, `U→V`.
5. Код не несе змісту (не містить назви/категорії) — його можна безпечно друкувати, а річ перейменувати.
6. 32^7 ≈ 3,4·10^10 комбінацій: колізії виключені практично, генерація перевіряє унікальність.

## 4. QR-вміст

`{BASE_URL}/t/{CODE}` — URL. Телефон відкриває його штатною камерою без застосунку.
`BASE_URL` задається в конфігурації; **змінювати його після друку міток не можна** (див. `QUESTIONS.md`, питання про хостинг/домен).

## 5. Маршрути

| Маршрут | Призначення |
|---------|-------------|
| `/t/<code>` | Резолвер QR. Авторизований → картка речі; ні → публічна картка («власність … , контакт») |
| `/` | Список/пошук речей, фільтри за статусом |
| `/items/new`, `/items/<id>` | Створення, картка, дії (передача, подія, мітки) |
| `/find` | Пошук за кодом (з нормалізацією) або текстом — запасний шлях без QR |
| `/labels` | Друкований аркуш QR-міток |
| `/holders` | Довідник власників |
| `/login`, `/logout` | Вхід (ім'я виконавця + спільний пароль) |

## 6. Безпека

1. Усі внутрішні сторінки — за авторизацією. Публічно доступна лише `/t/<code>` з мінімумом даних.
2. CSRF-токен у кожній POST-формі.
3. Пароль і секрет сесії — зі змінних оточення (`APP_PASSWORD`, `SECRET_KEY`).
4. Публічна картка не розкриває власника, вартість, серійний номер.
5. Для MVP — один спільний пароль + ім'я виконавця для журналу. Окремі акаунти/ролі — поза MVP.

## 7. Тестування

`pytest`: генерація/валідація кодів, повний цикл (створення речі → випуск мітки → скан → передача → заміна мітки), перевірка публічної картки й захисту сторінок.
