# Вимоги та контекст

## 1. Задача

Облік туристичного спорядження, що перебуває на балансі організації. Ідентифікація — через QR-коди.

## 2. Чому це складно (ключові обмеження)

1. **Мітки складно закріпити.** Спорядження різне: тканина, метал, пластик, мотузки, карабіни, намети, спальники.
2. **Умови експлуатації жорсткі.** Мітки стираються, псуються, мокнуть, замерзають, брудняться.
3. **Не можна використовувати лаки, клеї тощо.** Вони руйнують структуру матеріалів (тканини, стрічки, мотузки, пластики).
4. **Власники спорядження змінюються.** Одиниця спорядження переходить між людьми/групами/складом, історія має зберігатись.

## 2a. Уточнення замовника (актуальне)

1. В адмінпанелі: налаштування генерації QR, розмір кодів, експорт у PDF.
2. На мітці: QR + поруч номер ID.
3. QR = посилання на сторінку перегляду + ID (відкриває одразу потрібний предмет). Більше нічого в коді немає.
4. Посилання береться автоматично з хосту або задається полем в адмінці.
5. Усі дані (назва, фото, ...) — в маленькій базі, що редагується в адмінці.
6. Система має бути базовою й хоститись на безкоштовному рівні Google Cloud або Azure.

Деталі — `04-admin-and-qr.md`. Розділи нижче — ширша початкова чернетка.

## 3. Висновки, що визначають дизайн

Ці висновки — основа архітектури. Вони випливають із обмежень вище.

1. **QR-код — лише вказівник, а не носій даних.** У коді зашито URL з коротким кодом мітки. Усі дані живуть у базі. Тому пошкоджену мітку можна замінити, а дані не втрачаються.
2. **Річ (Item) і мітка (Tag) — різні сутності.** Одна річ може мати кілька міток одночасно (резервування) і змінювати їх протягом життя. Стара мітка після заміни **продовжує працювати** (веде на ту саму річ), якщо ще читається.
3. **Мітка має бути читабельною і без сканера.** Біля QR друкується короткий код (напр. `K7M2-9QX4`), який можна ввести вручну. Алфавіт без схожих символів (без `O/0`, `I/1/L`), є контрольний символ — помилку введення видно одразу.
4. **Стійкість QR до пошкоджень.** Корекція помилок рівня H (~30% площі можна втратити), великі модулі, високий контраст, тиха зона.
5. **Без хімії на спорядженні.** Мітка кріпиться механічно/без впливу на матеріал (див. `03-labeling.md`): пришита текстильна стрічка, бирка на кабельній стяжці/кільці, металева бирка, гравіювання там, де це безпечно для виробу. Вибір — на розсуд відповідального, система підтримує будь-який тип.
6. **Є запасний шлях пошуку без мітки.** Пошук за назвою, інвентарним номером, серійним номером, власником. Річ без читабельної мітки не «втрачається» з обліку.
7. **Журнал подій append-only.** Передачі, перевірки, ремонти, заміни міток, списання — записуються й не редагуються. Це дає історію власників і підзвітність.
8. **Польові умови.** Інтерфейс мобільний, мінімум кліків; сторінка сканування легка (слабкий зв'язок).

## 4. Функціональні вимоги (MVP — реалізовано)

| № | Вимога |
|---|--------|
| 1 | Реєстр спорядження: назва, категорія, інвентарний номер, серійний номер, опис, дата придбання, вартість, статус |
| 2 | Мітки: випуск, кілька на річ, тип/місце кріплення, статуси (активна / пошкоджена / втрачена / замінена) |
| 3 | Генерація QR (SVG) та друк аркуша наклейок/бирок заданого розміру |
| 4 | Сканування QR телефоном → картка речі (штатна камера, без додатка) |
| 5 | Ручне введення коду та пошук без мітки |
| 6 | Власники (особа / група / склад) і передача речі з історією |
| 7 | Події: перевірка наявності (інвентаризація), ремонт, нотатка, зміна статусу, списання |
| 8 | Заміна пошкодженої мітки зі збереженням історії |
| 9 | Публічна картка для сторонніх (хто знайшов річ): лише назва організації та контакт, без внутрішніх даних |
| 10 | Авторизація співробітників; кожна дія записується з іменем виконавця |

## 5. Поза MVP (див. `QUESTIONS.md`)

Фото речей, ролі й права, імпорт з Excel/1С, експорт для бухгалтерії, офлайн-режим (PWA), сповіщення про прострочену перевірку/ремонт, масове сканування камерою в браузері, інтеграція з бухгалтерією.
