# Адмінпанель, QR-коди та експорт у PDF

Спрощена модель (замінює складнішу модель «річ + мітки + події» з ранніх чернеток): **QR-код несе лише посилання + ID-шку. Усі дані про предмет лежать у базі й редагуються в адмінпанелі.**

## 1. Принцип

1. QR-код = `{BASE_URL}/i/{ID}`. Нічого іншого в коді немає.
2. Телефон сканує код → відкривається сторінка перегляду саме цього предмета.
3. Дані предмета (назва, фото, ...) зберігаються в базі й редагуються в адмінці без перевипуску QR.
4. Змінити назву, фото чи опис можна будь-коли — надрукований QR лишається дійсним.

## 2. Дані предмета (в базі)

1. `id` — число, автоінкремент; саме воно друкується біля QR.
2. `name` — назва елементу.
3. `photo` — фотографія (файл, стиснений при завантаженні до ~1200 px).
4. Решта полів — **уточнити** (повідомлення замовника обірвалося на «назва елементу, фотографія, …»). Кандидати: опис, категорія, статус, відповідальний, нотатки.

Таблиця `items` — єдина обов'язкова. Додаткові таблиці (власники, журнал) — лише якщо замовник підтвердить, що вони потрібні.

## 3. Налаштування QR (адмінпанель → «QR-коди»)

1. **Базове посилання (`BASE_URL`)**: два режими на вибір.
   1. *Автоматично* — береться з адреси, за якою відкрито адмінку (`request.host_url`).
   2. *Вручну* — поле в адмінці (напр. `https://gear.example.com`). Має пріоритет, якщо заповнене.
   Поточне значення та приклад підсумкового посилання показуються на сторінці налаштувань.
2. **Розмір QR** — у мм (напр. 20 / 25 / 30 / 40), задається в налаштуваннях.
3. **Розмір підпису з ID** — розмір шрифту номера біля QR.
4. **Розкладка на аркуші** — формат A4, відступи, автоматичний розрахунок кількості міток у рядку/на сторінці за розміром мітки.
5. **Вибір, що друкувати** — діапазон ID (`1–50`), окремі ID, або «усі предмети».
6. Корекція помилок QR — рівень H (за замовчуванням), величина тихої зони ≥ 4 модулі.

Налаштування зберігаються в таблиці `settings (key, value)`.

## 4. Експорт у PDF

1. Кнопка «Експорт PDF» на сторінці QR-кодів.
2. Кожна мітка: **QR-код + поруч номер ID** (напр. `№ 0042`).
3. Розмір мітки = обраний розмір QR + місце під ID; навколо — тонка лінія різання (за бажанням).
4. Реалізація: бібліотека `reportlab` (генерація PDF) + `segno` (QR як вектор). Вектор дає чіткий друк за будь-якого розміру.
5. Попередній перегляд — той самий PDF у новій вкладці.

## 5. Сторінка перегляду предмета (`/i/<id>`)

1. Публічна, лише читання, легка (слабкий зв'язок у полі).
2. Показує: назву, фото, інші поля предмета.
3. Редагування — лише в адмінпанелі (за паролем).

## 6. Адмінпанель

| Розділ | Призначення |
|--------|-------------|
| Предмети | Список, додавання, редагування (назва, фото, ...), видалення |
| QR-коди | Налаштування (посилання, розмір), вибір ID, експорт PDF |
| Вхід | Один пароль адміністратора (`ADMIN_PASSWORD` у змінній оточення) |

## 7. Хостинг на безкоштовному рівні

Мета — максимально простий проєкт: один Flask-процес, SQLite-файл, папка з фото.

1. **Рекомендовано: Azure App Service, тариф F1 (Free), Linux.** Постійне сховище `/home` зберігається між перезапусками, тож SQLite-файл і фото лежать там без змін коду.
   1. Обмеження F1: щоденна квота CPU, холодний старт після простою, невелике місце на диску, без власного домену з SSL.
   2. Адреса `*.azurewebsites.net` — стабільна, але прив'язана до імені застосунку: після друку QR її змінювати не можна.
2. **Альтернатива: Google Cloud Run (free tier).** Файлова система тимчасова, тому SQLite там **не підходить**; потрібні Firestore (дані) та Cloud Storage (фото). Це додає код-адаптери — складніше за варіант 1.
3. Умови безкоштовних рівнів змінюються — перед розгортанням звірити актуальні ліміти на сайтах провайдерів.
4. Резервна копія: періодично завантажувати `gear.db` і папку фото (адмінка може віддавати ZIP).

## 8. Змінні оточення

1. `ADMIN_PASSWORD` — пароль адмінки.
2. `SECRET_KEY` — підпис сесії.
3. `BASE_URL` — необов'язково; якщо задано, має пріоритет над автовизначенням (інакше — поле в адмінці, інакше — авто).
